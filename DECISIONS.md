# Decisions

Product and engineering calls made during the build, newest last.

1. **Browser agent is a fallback, not banned.** The brief's principle 7 forbade automating Swiggy/Zomato/etc.; the owner then asked for exactly that. Rule now: official route first (MCP / API / ONDC / deep link); otherwise the browser agent drives the user's *own* logged-in session in a separate Chromium profile, visibly, with approval at every submit/checkout, and never enters payment details. Known risk: may breach those sites' terms and break when their UI changes.
2. **Core runs on Node with native TypeScript type stripping** (no build step in dev). Released apps bundle core with esbuild and ship it with a Node runtime as a Tauri sidecar.
3. **SQLite via Node's built-in `node:sqlite`** with Kysely through a tiny adapter — no native modules to rebuild per platform.
4. **The master key lives in the OS keychain, read by the Tauri (Rust) shell** and handed to core over stdin at launch. Core never touches the keychain directly, so the same core can later run in the cloud with a KMS-backed `KeyProvider`.
5. **Model adapters are hand-written** (Anthropic Messages API + one OpenAI-compatible adapter that covers OpenAI, Gemini's OpenAI endpoint, OpenRouter and Ollama). Fewer dependencies, full control over streaming tool calls.
6. **Taint tracking for prompt injection.** Once a run has read untrusted content (email, web page, browser), "Always allow" rules are suspended for the rest of that run and every `act` needs an explicit click. The card says why.
7. **Money is never auto-approved** and money actions above the per-action spending cap cannot be approved until the cap is raised in Settings.
8. **Google and Payments are native (in-process) connectors; Food and Travel are MCP servers.** Native where OAuth tokens / encrypted secrets / QR rendering are needed; MCP everywhere else, so third-party servers plug in the same way.
9. **MCP tools carry RelayIt `_meta`** (`relayit/class`, `relayit/previewTool`, …). Approval cards for MCP `act` tools are built by calling a server-side preview tool, so amounts on cards come from the server, never from model-written arguments.
10. **Profile, addresses, model config and settings live in a key-value table** rather than separate tables; they are single-row documents.
11. **Sign-ins for the browser agent happen in a visible RelayIt browser window, by the user.** Instead of a masked password box, the user signs in to Swiggy/Zomato/etc. themselves; the session lives only in the dedicated Chromium profile. The model never sees a password, and the browser tools refuse to type into password, OTP, card, CVV or UPI PIN fields.
12. **Official MCP servers first.** Swiggy (Food, Instamart, Dineout), Zomato and Wispr Flow publish official remote MCP servers; they're one-click presets with OAuth. The browser agent is only for services with no official connection.
13. **"Can wait" email is not a task.** Triage puts "needs you" mail on the Tasks board and keeps "can wait" as a collapsible list, so Done means done.
14. **The release sidecar is the official Node build**, downloaded and SHA-256-verified against nodejs.org by `scripts/bundle-core.mjs` (package-manager Node builds link to shared libraries and can't be shipped).
15. **Debug builds use a separate keychain item and data folder** (`…/dev`) so a dev build never prompts for or corrupts an installed release's data.
16. **Order tracking**: when `place_order` succeeds, core records the order, creates the UPI request and watches the payment (Razorpay test/mock link status, or the user's "I've paid"); once paid it confirms the order with the food server.
17. **Accessibility over the palest greys.** The audit (docs/a11y-audit.md) showed the original muted/faint greys and white-on-ember buttons missed WCAG AA. Tokens were darkened just enough to pass (ember accent #c4471f, muted #5d574f, faint #6c665e in light; faint #9a938a and dark text on ember buttons in dark). Field and switch borders use a 3:1 `--control-border`. Focus is a solid accent outline.
18. **Money holds are cancellable.** Hold-to-approve stops if the key/pointer is released, focus leaves, the button is disabled, or the card unmounts — a hold can never complete off-screen.
19. **Intent fixes from the eval harness (evals/FINDINGS.md).** Assistant tool calls are never aliased with the work queue (a real transcript bug); a turn that ended with quick-reply choices continues with its full tool context; the router knows "what needs me today" and "tell my manager"; tool descriptions spell out the food ID flow, email search-before-asking, ISO datetimes; the prompt forbids status/price claims not backed by a tool result in the current task; browser tools are hidden when the browser agent is off; train search reports available classes instead of an empty list.
